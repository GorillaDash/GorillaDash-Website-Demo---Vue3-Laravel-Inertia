## Project

"Hungry Gorilla" (placeholder — rename via `bin/new-client.sh`) — the GorillaDash client-site starter: a Laravel 13 + Inertia v3 + Vue 3 SPA that renders CMS-driven pages from the GorillaDash GraphQL API, with runtime multi-locale routing, CMS-renamable page paths, Cloudflare edge-cached HTML, and a GKE (Kustomize) deployment. Clone per client site; onboarding steps live in `docs/NEW-CLIENT-CHECKLIST.md`.

## Architecture

- **Server-driven SPA via Inertia.** Controllers/routes return `Inertia::render('PageName', [...props])` (or `Route::inertia()` for prop-less pages) instead of Blade views. There is no client-side router and no REST API layer — props are the data contract between Laravel and Vue.
- **A sub-route's controller validates its open params; it never fetches the page's content.** A `{slug}`-shaped parameter matches ANY segment, so without a check the route renders an empty page at 200 and search engines index it as real — a soft 404, which the edge then caches under that URL. Each open param gets a small server-side service answering one question — does this exist — as cheaply as it can (`App\Services\BoundLocation`, behind `{page}/{slug}`, is the worked example; `TheGreatGreek-inertiajs` and `GrazeCraze-inertiajs` add `Articles` for a `{newsId}` and `FoodMenu` for a `{section}/{item}`), bound `scoped` so a newly published record is routable on the next request. **Split the two failure modes: a definitive miss 404s, a lookup FAILURE is let through** — a CMS outage must never 404 a whole catalogue. Mind which GD query you check WITH: `article(slug:)` answers `null` for an unknown slug and so IS usable as its own existence check, but `foodMenuListItem` answers "Internal server error", which makes a miss and an outage indistinguishable — read the parent list instead. And `article(slug: "")` is a WILDCARD returning the newest article, so reject a blank value before it reaches GD. The CONTENT is always fetched client-side through Apollo, on these routes exactly like on every other page: Inertia hands the SSR renderer a page object and takes back `{ head, body }` (`resources/ts/ssr.ts`), so Vue cannot set an HTTP status — a frontend "no data, therefore 404" is a soft 404, and SSR may be off or unreachable anyway.
- **Vue pages** live in `resources/ts/pages/` (one `.vue` file per Inertia page), **not** `resources/js/Pages` — this project was renamed from `resources/js` to `resources/ts` (see commit `fcb88d0`). Boost's `pagesDirectory()` autodetection doesn't know about this rename, so `php artisan boost:update` will periodically regenerate the guideline/skill files with the wrong `resources/js/Pages` path; treat this line as authoritative and ignore any conflicting text. Entry point is `resources/ts/app.ts`; shared types in `resources/ts/types/`; helpers in `resources/ts/lib/utils.ts`.
- **Static assets via GCS/CDN, not Vite.** Images are not bundled — source files live in `public/static/images/{icon,logo,bg,menu}/` and sync to Cloud Storage with `pnpm run static:upload`. In Vue, reference them through the path helpers in `resources/ts/lib/gcs.ts` (`iconPath`, `logoPath`, `bgPath`, `menuPath` — one per folder), based at `VITE_GCS_STATIC_URL` — e.g. `` `${bgPath}/hero-bg.jpg` ``, as `HomeHero.vue` does. Do not re-introduce `import … from '@/assets/…'`. Files must be uploaded for images to appear (dev hits the CDN too).
- **GD CMS data comes in three shapes, and mixing them up is the usual first mistake.** _Page contents_ — a page's own fields — are read off the `websitePage` with `getValueByName()` / `getImageByName()` (`resources/ts/services/websiteContentValue.ts`); a standalone named section uses `getWebsiteSection()` (`api/websiteContents.*`). _Website components_ are REPEATABLE lists — callout cards, tiles, values, timeline entries — fetched by component type with `useWebsiteComponent(name, map)` (`resources/ts/services/websiteComponents/`), which each site wraps in a named service that maps to a typed view model. _Articles_ are the editorial collection behind news/press/blog, sliced by CATEGORY: `getArticlesByCategories({ categories: ['In The News'], page, itemsPerPage })` and `getArticle(slug)` (`api/article.*`), with `formatCmsDate()` from `lib/dates.ts` for their timestamps — that helper does no timezone conversion on purpose, because a CMS date is a calendar date and converting it hydration-mismatches (see `tests/js/cmsDate.test.ts`). Note `api/websiteMenus.*` is site NAVIGATION, not a food menu.
- **Per-store CTA links.** Order / Delivery / Catering / Gift Card buttons on a franchise site never point at a fixed URL — each store sets its own in GD (Settings → Website tab), stored as ordinary tribe _contents_ named `Order URL`, `Deliver URL`, `Catering URL`, `Gift Card URL`. There is no helper here for them on purpose: not every client uses them, and what a CTA should do when a store has no link of a given kind — hide it, disable it, open a store picker, fall back to a national URL — is a product decision that differs per brand and per country. A site that needs them reads them off a tribe it already fetched with `getValueByName('Order URL', tribe)`, and should treat `''` as "no link": clearing the field in the CMS leaves an empty string, and a CTA pointing at `""` reloads the current page instead of doing nothing. `TheGreatGreek-inertiajs` has a worked version if you want one to copy.
- **`app/Http/Middleware/HandleInertiaRequests.php`** defines globally-shared props (auth, flash, etc.) available to every page — add cross-cutting page data here.
- **Wayfinder** (`@laravel/vite-plugin-wayfinder`) generates typed TS functions from Laravel routes/controllers. Import route helpers from `@/routes/` (named routes) and `@/actions/` (controllers) rather than hardcoding URLs; regenerate via the vite plugin on build/dev (configured with `path: 'resources/ts'` in `vite.config.ts`). The generated `resources/ts/{routes,actions}/` are gitignored, so a fresh checkout has none until you build. Nothing imports them today (every CMS-driven path is built at runtime — see `gd-locale-links`), so `types:check` passes on a bare checkout; the moment you add the first `@/routes/*` or `@/actions/*` import it will fail there until you run `pnpm run build`, or the standalone `php artisan wayfinder:generate --path=resources/ts` (never the bare command — it defaults to `resources/js`).
- **Styling** is Tailwind CSS v4 (configured through the `@tailwindcss/vite` plugin, not a `tailwind.config.js`). **Write classes in Tailwind's canonical form** — the scale before square brackets: v4's spacing scale is `0.25rem × n`, so `min-h-[26rem]` is `min-h-104`, `max-w-[87rem]` is `max-w-348` (and `max-w-[56rem]` is `max-w-4xl`), `border-b-[10px]` is `border-b-10`, `rounded-[1.5rem]` is `rounded-3xl`, `aspect-[4/5]` is `aspect-4/5`, `-ml-[6%]` is `ml-[-6%]`, `!bg-white` is `bg-white!`. `pnpm run tw:scale` (`bin/tailwind-scale.mjs` — Tailwind's own `canonicalizeCandidates`, loaded against `app.css`) rewrites all of that; it runs inside `pnpm run lint` and on commit, and `pnpm run lint:check` (CI, `composer ci:check`) fails on leftovers. Pass `--rem=16` to also fold px onto the rem scale. Beyond what it rewrites, **prefer the built-in vocabulary over brackets at all**: a `text-*` ladder over `clamp()`, fractions (`left-5/6`, `w-1/5`) over `[84%]`, `grid-cols-7` + spans over `[57fr_43fr]`, the nearest rung (`rounded-3xl`, `size-21`, `tracking-wider`) over an odd px, a named breakpoint or `--breakpoint-*` token over `min-[…px]` — and any arbitrary breakpoint in rem, never px, so it sorts with the ladder. A bracket is the exception, with a comment saying why (rules and table: `gd-frontend-architecture` → Canonical classes).
- **SSR** is built with `@inertiajs/vite` (`pnpm run build:ssr`); it works automatically in vite dev mode with no separate Node server.
- **i18n via Tolgee** (`@tolgee/vue`). All user-facing text goes through `useTranslate()` — `t(...)` in templates (the ref auto-unwraps), `t.value(...)` in `<script>`. Config is **runtime, per-country**: `TOLGEE_CDN_URL`/`TOLGEE_API_URL`/`TOLGEE_API_KEY` env → `config('services.tolgee.*')` → `HandleInertiaRequests` → `page.props.config` → `runtimeConfig()`; the instance is built by `createTolgee()` in `resources/ts/inertiaApp.ts` (after `setRuntimeConfig`), not a `VITE_*` build-time value. Key convention: short text → source-as-key `t('Log In', 'Log In')`; sentence-with-variable → namespaced + ICU `t('locations.hero.distance', '{miles} miles from {city}', { miles, city })`; strip trailing punctuation (`...`/`:`/`!`/`.`) from keys and append as a literal. **Do not** translate CMS content (`getValueByName`/`*Service`), enum/label maps (e.g. `serviceMeta` in `LocationHero.vue`), fake `// TODO` data, brand/store names, or numbers. **A module that is not a component takes the translate function as a parameter, and that parameter must be named `$t`** — Tolgee's key extractor only follows a `t` it can trace to a `useTranslate()` in the SAME file, while `$t` it treats as the app-global `@tolgee/vue` installs and extracts anywhere; name it `t` and `tolgee sync` skips every string in the file with a warning, while the page still renders its inline defaults, so nothing looks wrong. Full details in the `gd-frontend-architecture` skill.

# Inertia

- Inertia creates fully client-side rendered SPAs without modern SPA complexity, leveraging existing server-side patterns.
- Components live in `resources/ts/pages` (unless specified in `vite.config.ts`) — this project was renamed from `resources/js` to `resources/ts`; do not use `resources/js/Pages`. Use `Inertia::render()` for server-side routing instead of Blade views.
- ALWAYS use `search-docs` tool for version-specific Inertia documentation and updated code examples.
- IMPORTANT: Activate `inertia-vue-development` when working with Inertia Vue client-side patterns.

# Inertia v3

- Use all Inertia features from v1, v2, and v3. Check the documentation before making changes to ensure the correct approach.
- New v3 features: standalone HTTP requests (`useHttp` hook), optimistic updates with automatic rollback, layout props (`useLayoutProps` hook), instant visits, simplified SSR via `@inertiajs/vite` plugin, custom exception handling for error pages.
- Carried over from v2: deferred props, infinite scroll, merging props, polling, prefetching, once props, flash data.
- When using deferred props, add an empty state with a pulsing or animated skeleton.
- Axios has been removed. Use the built-in XHR client with interceptors, or install Axios separately if needed.
- `Inertia::lazy()` / `LazyProp` has been removed. Use `Inertia::optional()` instead.
- Prop types (`Inertia::optional()`, `Inertia::defer()`, `Inertia::merge()`) work inside nested arrays with dot-notation paths.
- SSR works automatically in Vite dev mode with `@inertiajs/vite` - no separate Node.js server needed during development.
- Event renames: `invalid` is now `httpException`, `exception` is now `networkError`.
- `router.cancel()` replaced by `router.cancelAll()`.
- The `future` configuration namespace has been removed - all v2 future options are now always enabled.
